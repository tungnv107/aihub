# Sub2API test — sửa giới hạn request 2 MiB

Ngày 30/10/2026, endpoint `https://sub2api-test.tudonghoa.me/v1/responses` trả `413 Payload Too Large: Request body too large, limit is 2MB`. Request ID khách cung cấp được tìm thấy trong log gateway với trạng thái 413; không cần lấy nội dung hội thoại hay credential khách để chẩn đoán.

## Nguyên nhân và phạm vi

Service `relay-ui` trong `/opt/independent-relay-test/compose.yaml` đặt cả `GATEWAY_MAX_BODY_SIZE` và `GATEWAY_TEXT_MAX_BODY_SIZE` bằng `2097152`. Relay phía sau chưa có override `relay.max_body_bytes`, nên dùng mặc định core cùng mức 2 MiB. Route Caddy của domain không đặt giới hạn body riêng.

Vì vậy chỉ nâng gateway sẽ để lại một điểm chặn 2 MiB ở relay. Đây là lỗi cấu hình server; hotfix desktop 0.3.2 trên máy khách không sửa được cấu hình này.

## Thay đổi đã áp dụng

Lúc **09:21 UTC ngày 30/10/2026**, đặt ba giá trị sau bằng `67108864` (64 MiB):

- `GATEWAY_MAX_BODY_SIZE` trong environment service `relay-ui`.
- `GATEWAY_TEXT_MAX_BODY_SIZE` trong cùng service.
- `relay.max_body_bytes` qua admin API của relay, lưu bền vững trong SQLite.

Chỉ recreate container `independent-relay-test-relay-ui-1`, dùng nguyên image có sẵn. Relay áp dụng setting động. So sánh container ID và thời gian khởi động xác nhận relay, PostgreSQL, Redis, Sub2API production, Caddy, admin, license và distribution không bị restart. Không thay policy, tài khoản, refresh token hoặc database ứng dụng gateway.

Bản sao cấu hình trước sửa nằm tại `/opt/independent-relay-test/backups/body-limit-20261030T092150Z/`. Thư mục có quyền 0700; Compose backup có quyền 0600. `before.json` ghi các giới hạn và trạng thái container, không chứa key.

## Kiểm chứng

Trước sửa, request thử **9.437.184 byte (9 MiB)** bị trả 413 ở cả HTTPS gateway lẫn relay nội bộ. Request nhỏ 1 KiB đi đến kiểm tra JSON và trả 400.

Sau sửa, cùng request 9 MiB đi đến kiểm tra JSON và trả 400 ở cả hai tầng; trong phép thử này JSON được cố ý làm hỏng để không gọi model. Trạng thái 400 này chứng minh đã qua bộ đọc body, không phải một lượt inference thành công.

Tiếp đó, hai lượt inference có body HTTP 9 MiB đều trả **200** và câu trả lời `TDH_BODY_LIMIT_OK`: một lượt qua domain HTTPS thật, một lượt gọi trực tiếp relay. Body gồm JSON hợp lệ với prompt ngắn và khoảng trắng đệm; khoảng trắng kiểm tra kích thước truyền tải, không tạo hội thoại 9 MiB cần model xử lý. Điều này xác nhận giới hạn HTTP đã được nâng, không chứng minh model chấp nhận 9 MiB nội dung hội thoại hoặc toàn bộ giới hạn context.

Kết quả kiểm chứng lưu trên VPS tại `/opt/independent-relay-test/body-limit-verification.json`, thời điểm **09:22:29 UTC**. Không lưu request body, token hay câu trả lời khách hàng vào báo cáo.

Kiểm tra biên lúc **09:25:24 UTC** xác nhận cả HTTPS gateway và relay nội bộ nhận body đúng **67.108.864 byte** đến bước kiểm tra JSON (400 với dữ liệu cố ý sai), còn **67.108.865 byte** bị chặn 413. Như vậy không còn tầng trung gian giới hạn thấp hơn 64 MiB trong đường đi đã thử, và giới hạn hữu hạn vẫn được giữ. Báo cáo: `/opt/independent-relay-test/body-limit-boundaries.json`.

## Công cụ vận hành

Source:

- [Kiểm tra cấu hình chỉ đọc](../test/vps_inspect_sub2api_body_limit.py).
- [Áp dụng và kiểm chứng có giới hạn phạm vi](../test/vps_fix_sub2api_body_limit.py).

Chạy script trên chính VPS, bằng sudo để đọc cấu hình đã có. Script không nhận key trên command line:

```bash
sudo python3 /tmp/vps_fix_sub2api_body_limit.py --probe
sudo python3 /tmp/vps_fix_sub2api_body_limit.py --apply
sudo python3 /tmp/vps_fix_sub2api_body_limit.py --verify
sudo python3 /tmp/vps_fix_sub2api_body_limit.py --boundaries
```

`--probe` gửi dữ liệu JSON lỗi, không gọi model. `--apply` kiểm tra baseline, đối chiếu toàn bộ Compose để chỉ cho phép đổi hai environment, sao lưu, cập nhật relay, recreate riêng gateway và kiểm tra lại. Nếu bước triển khai/kiểm chứng cấu hình thất bại, script khôi phục giới hạn cũ. Khi đã ở 64 MiB, chạy lại `--apply` chỉ kiểm tra, không restart.

`--verify` thực hiện hai inference nhỏ trên tài khoản test đã cấu hình, có thể tiêu thụ quota thông thường. Header chứa key được truyền cho curl qua file ẩn danh trong RAM; không đặt key trong argv hay file trên đĩa. HTTPS vẫn kiểm tra chứng chỉ bình thường.

`--boundaries` gửi JSON lỗi ở đúng giới hạn và vượt 1 byte, lần lượt qua hai endpoint. Không gọi model, nhưng cần khoảng trống RAM và thời gian phù hợp cho bốn request cỡ 64 MiB.

## Khôi phục thủ công khi cần

Đọc `before.json` để xác định giới hạn cũ. So sánh Compose hiện tại với backup; nếu có thay đổi mới của người vận hành, chỉ hoàn nguyên hai dòng giới hạn tương ứng, không ghi đè toàn bộ cấu hình mới. Gửi giá trị cũ của `relay.max_body_bytes` qua admin API rồi recreate riêng service `relay-ui` bằng `docker compose up -d --no-deps --no-build --pull never relay-ui` trong thư mục triển khai. Kiểm tra health và giới hạn thực tế sau khôi phục.

Không phục hồi SQLite cũ chỉ để đổi giới hạn body: việc đó có thể làm lùi trạng thái tài khoản/refresh token. Mức giới hạn cũ 2 MiB sẽ làm request lớn bị 413 trở lại.

## Khách hàng cần làm gì

Gửi lại request tới domain đang dùng; không cần đổi API key hay cài lại ứng dụng cho hotfix server này. Nếu endpoint lỗi là `127.0.0.1:18455` với `compressed_request_rejected`, áp dụng [hướng dẫn cập nhật desktop 0.3.2](PATCH-0.3.2.md) trên máy đó. Mỗi giới hạn được xử lý tại đúng thành phần đang nhận request.
